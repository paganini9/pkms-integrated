# RB(요구거동) 저작 UX 검토 — 도메인 지식(M1) ↔ 프로젝트 요구·설계(M2)

> 작성일 2026-07-09 · 상태 draft-v0.1 · 열린 항목 "RB 저작 UX" 검토 결과.
> 결정: **RB는 프로젝트 요구사항(M2 데이터)이며, 엔지니어가 자연어로 입력(커스텀 빌더)한다.** 화면·시나리오에 두 입력을 명확히 구분해 반영한다.

---

## 1. 핵심 구분 — 두 종류의 입력은 데이터 성격이 다르다

| | **도메인 지식 입력** | **프로젝트 요구·설계 입력** |
|---|---|---|
| 무엇 | SPMM 기반 일반 설계 지식 | 특정 제품 프로젝트의 요구·설계 |
| 예 | "겨울철 고무는 소음을 유발한다" | "이 겨울용 SUV 프로젝트는 소음이 없어야 한다" |
| 성격 | 재사용·범용 (프로젝트 무관) | 프로젝트 종속 데이터 |
| 온톨로지 층 | **M1 (도메인 지식)** | **M2 (프로젝트 데이터)** |
| 산출 | 개념·관계·6문장·DesignRule | Project · RequiredBehavior(요구) · DesignedBehavior(설계) |
| 입력 흐름 | SC-1 SmartInput → 추출 → 검증 → M1 | 신규: 자연어 요구 → RB 절 파싱 → 프로젝트 저장 |
| 소유·거버넌스 | 관리자 큐레이트 + 엔지니어 기여 | 프로젝트 담당 엔지니어 |

> 이전 TTL 데모는 `RB_Winter`·`RB_NoChatter`를 **M1**(도메인)에 두었으나, 본 검토에 따라 **M2(프로젝트)** 로 이동한다. RB는 "지식"이 아니라 "이 프로젝트가 요구하는 것"이다.

---

## 2. 개념 모델 — Project(M2)

```
Project (예: eng:Proj_WinterSUV)
  ├─ 대상 컨텍스트: 차종=중형 SUV, 환경=겨울철
  ├─ hasRequirement → RequiredBehavior[]   (요구, 자연어 입력)
  │     RB1 = 소음 없음 (forbids Noise)
  │     RB2 = 끝단 떨림 없음 (forbids TipChatter)
  └─ hasDesign → DesignedBehavior/설계 인스턴스[]   (설계)
        Blade_A = 재질·길이·스프링·형상 …
satisfy(project) : 각 설계 DB ⊑ (프로젝트 요구 ⊓) 를 M1 도메인 규칙으로 판정
```

- RB/DB는 M2 개체이고, M2→M1은 `rdf:type`/참조. 판정 근거(6문장 규칙)는 M1.
- 요구가 참조하는 증상·조건(Noise·Winter 등)은 **M1에 존재해야** 한다. 없으면 "도메인 지식 먼저 필요" 플래그 → 지식 입력으로 유도(두 흐름의 자연스러운 연결).

---

## 3. RB 저작 UX — 자연어 커스텀 빌더 (생성기–검증기 재사용)

1. 엔지니어가 **프로젝트 선택/생성** → 대상 컨텍스트(차종·환경) 설정.
2. **자연어로 요구 입력**: 예) "겨울철 저온에서도 와이퍼 소음이 없어야 하고, 중형 SUV에서 끝단 떨림이 없어야 한다."
3. **LLM 파싱 → RB 절**(M1 증상·조건에 그라운딩): `¬∃exhibits.Noise ⊓ ¬∃exhibits.TipChatter`, 컨텍스트 {Winter, MidSizeSUV}. 구조화 미리보기 표시.
4. **검증**: 참조 증상·조건이 M1에 있는지 확인(없으면 경고 + 지식 입력 유도). 모순(예: 서로 배타적 요구) 점검.
5. 엔지니어 **확인·편집** → 프로젝트 요구셋으로 **저장**(명명·재사용).

> SmartInput(도메인 지식 추출)과 같은 생성기–검증기 패턴이되, **산출이 도메인 트리플이 아니라 프로젝트 RB**라는 점만 다르다. 인프라(AI Gateway·검증) 재사용.

## 4. 시나리오에 넣을 추가 엔지니어 입력 문장 (6문장 외, 프로젝트 요구)

도메인 지식 6문장(S1~S6)은 그대로 두고, **프로젝트 요구 문장**을 예시로 추가한다.

| ID | 유형 | 문장(엔지니어 자연어 입력) | 파싱 결과 |
|----|------|----------------------------|-----------|
| PR-1 | 요구(RB) | "겨울철 저온에서도 와이퍼 소음이 없어야 한다." | forbids Noise @Winter |
| PR-2 | 요구(RB) | "중형 SUV에서 끝단 떨림이 발생하지 않아야 한다." | forbids TipChatter @MidSizeSUV |
| PR-3 | 요구(RB, 확장 유도) | "장마철 폭우에서도 시야가 확보되어야 한다." | forbids 시야미확보 @폭우 — **M1에 없는 증상** → 지식 입력 유도 |
| PD-1 | 설계(DB) | "이 프로젝트 블레이드는 실리콘·550mm·12N·복합 암형상으로 한다." | 설계 인스턴스 |

- PR-3은 요구가 미지의 증상을 참조하는 경우를 보여주는 예 — 시스템이 "이 증상에 대한 도메인 지식이 없습니다. 먼저 지식으로 추가하시겠어요?"로 **두 흐름을 연결**한다.

## 5. 화면·시나리오 반영 (요약; Phase 2·4 갱신)

**IA 조정 — 엔지니어 워크스페이스를 두 영역으로**
```
엔지니어 워크스페이스
├── 도메인 지식 (프로젝트 무관, M1)
│    · 지식입력(SC-1) · 지식맵(SC-4)
└── 프로젝트 (프로젝트 선택자 ▾, M2)
     · 요구사항 정의(신규 SC-1P) · 설계 입력·검증 satisfy(SC-2) · 환각비교 Q&A(SC-3) · 설계안 비교(SC-5)
```

**신규 화면 S-02b — 프로젝트 요구사항 입력**: 프로젝트 선택/생성 → 자연어 요구 입력 → RB 절 파싱·미리보기·검증 → 저장. (S-02 지식입력과 시각적으로 구분: "지식" vs "프로젝트 요구")

**S-03 설계검증 재구성**: 프로젝트 컨텍스트에서 동작 — 프로젝트의 **요구셋 자동 로드** + 설계 입력 → satisfy. (요구를 매번 고르는 게 아니라 프로젝트에 이미 정의된 요구를 사용.)

**신규 시나리오 SC-1P — 프로젝트 요구사항 정의**: 트리거(새 프로젝트 요구 정의) → 자연어 입력 → RB 파싱·검증 → 저장. 예외: 미지 증상 참조 → 지식 입력 유도.

---

## 6. 확정 사항 & 후속

- RB = **M2 프로젝트 요구 데이터**, 자연어 커스텀 빌더로 입력. 도메인 지식(M1)과 화면·시나리오에서 분리.
- 형식화: 절은 운영표현(forbids)로 저장, `¬∃exhibits.증상` 형식은 미리보기·DL 증명 시 파생(EL+SHACL 유지).
- 후속: TTL 데모에 `Project` + M2 요구셋을 반영(RB를 m2로 이동), Phase 2·4 갱신본 반영.
