# 포스트-g3 문제 정의 · 현재 상황 · 개선 로드맵 (③ 실검증 결과 기반)

> 근거: `postg3-검증-결과.md`(신규 어휘 13문장, 저작 26회 중 저장 성공 사실상 0). 결함은 미수정(chore/postg3-validation).
> 헤드라인: **③이 제 일을 했다.** 실패는 LLM 품질이 아니라 **파이프라인 구조** — 저작 루프가 실제로 배선돼 있지 않다. g3는 6문장 시드(정적 rules.ttl·하드코딩 맵)로 §5를 통과한 **데모 경로**였고, "새 지식 저작→검증 반영"이라는 제품 핵심 약속은 미배선이다. 다음은 "④⑤ 폴리시"가 아니라 **저작 루프를 살리는 집중 스프린트**다.

---

## 1. 부수 확정 — A/B: 저작 기본 = Claude

신규 어휘에서 Claude ≫ Solar(복합어 5/5 vs 2/5 · 유령참조 0 vs 6 · "고무" 발명 0 vs 3 · 조건앵커 7 vs 5 · 차단성위반 15 vs 28). **저작=Claude 확정**(Solar 되돌림 근거 소멸). 단 Claude도 위반 15 — **마진이 구조 결함에 눌려** 아직 값을 못 냄. 스프린트 후 재측정.

## 2. 작동하는 토대 (여기 위에 쌓는다)

OOV 승인→접지 편입(오버레이 영속)은 설계대로 동작 · Q&A fail-closed · 위조 초안 409. → 어휘층·오버레이·접지 판정은 견고. 문제는 **저작 저장 경로**에 집중돼 있다.

## 3. 문제 6개 — 정의 · 현재 · 원인 · 개선

### P0 (버그·즉시) 라벨→IRI 새니타이징 없음 → 500 크래시
- **현재**: 공백 라벨("오존 노출")로 IRI 생성 시 크래시(`oxigraph.py:172`). violations 0인 완벽 초안도 저장이 죽고, "오존"으로 줄이면 201.
- **원인**: raw 라벨을 IRI에 직접 사용.
- **개선**: IRI는 슬러그/해시로 생성, 표면형은 `rdfs:label`로 보존. **다른 모든 저장의 선결 버그.**

### P1 (치명·핵심) 저작 → 규칙·Causation → 영속 → satisfy 다리가 없다
- **현재**: 저장은 트리플만 넣는다. `/rules`는 `rules.ttl` 정적 5개 그대로이고, 저장 응답의 `derived`는 **영속 안 되는 일회용 투영**. K2(오존→균열)를 완전 접지·저장(S11)해도 satisfy 판정이 **전혀 안 바뀐다**. T-91 Causation은 저장 그래프에 **0행**(호출부가 유닛 테스트뿐).
- **원인**: 컴파일러가 시드에서만 컴파일. 저작 파생분(규칙·Causation·SHACL)을 **영속 규칙집합/그래프에 편입하는 배선이 없다.** T-91이 저장 경로에 미연결(이항 우회 병 재발).
- **개선**: 저장 시 문장→구조화규칙→(Causation 노드 + SHACL + 인과엣지)를 **T-85식 오버레이로 영속**, 컴파일러·satisfy가 **시드 + 저작 오버레이를 함께** 소비. Causation을 저장 경로에 실제 배선. → **"저작한 지식이 산다."** (제품 핵심 약속 복원.)

### P2 (높음) 판정이 온톨로지 타입이 아니라 LLM 타입을 믿는다
- **현재**: `WiperBlade ⊑ PartType`인데 두 provider 다 Component로 붙임 → "고무 블레이드" 지식이 **어떤 provider로도 저장 불가**.
- **원인**: 검증이 추출 type(LLM이 붙인 것)을 신뢰. 라벨→IRI→온톨로지 canonical type 미사용.
- **개선**: 라벨→IRI 해석 후 **온톨로지 canonical type으로 치환**(LLM type은 힌트로만). T-73/어휘층 해석기 재사용. (P1이 저장하려면 선결.)

### P3 (치명/높음) 저작 경로에 안전·의미 게이트가 없다
- **3a 도메인 게이트 부재**: OOV가 warning이라 "타이어"도 저장된다. **"우회 9/9 차단"은 Q&A의 성질이지 저작의 성질이 아니었다** — 저작은 사실상 무방비.
- **3b 부정을 담을 자리 없음**: 술어 8종에 부정이 없어 "들뜸이 없어야 한다"가 `블레이드 -causes-> 들뜸`(**의미 반전**)으로 추출되고 `conforms=true`로 **승인 버튼이 열린다**(정반대 저장 위험).
- **3c OOV 거부 도달 불가**: 임베딩이 항상 top-k를 채워 `out_of_scope` 0(21/21 synonym_variant). 후보 오염 위험(경화→경도 0.99, 오존→경도 0.92 — 승인 시 접지 오염).
- **개선**: (a) 저작 저장에도 **도메인 게이트**(OOV 미해결분은 warning이 아니라 **승인 게이트**). (b) **부정/증상부재 1급화** — 술어에 부정/모달 추가, 또는 RB=증상부재(`owl:complementOf`, 열린항목 #5) 실제 구현. (c) OOV 후보 **임계값 + `out_of_scope` 경로 복구**, 저신뢰는 거부/명료화.

### P4 (치명) M1/M2가 안 갈린다 + RB 경로가 하드코딩
- **현재**: RB 증상 맵이 Noise·TipChatter **2종 하드코딩**(`misc.ts:15`) → R1~R8 requirements **0/8**. 유일 저장(R7)마저 **요구를 지식으로 오저장**(라우팅 부재).
- **원인**: RB 파싱이 고정맵. 입력을 "요구(must/must-not) vs 인과지식"으로 가르는 라우팅 없음.
- **개선**: (a) RB 증상 맵을 **온톨로지 Symptom 클래스·어휘층에서 동적**으로. (b) **입력 분류/라우팅**(LLM 분류 + 결정론 확인) 또는 UI에서 종류 강제 → 요구=M2 RB, 인과=M1. (P3b 부정과 자연 결합: 요구="증상 부재".)

### P5 (배선) OOV 승인·Causation이 BFF/UI에 노출 안 됨
- **현재**: `/oov/approve`가 지식서비스 직접만(BFF **404**) → UI에서 도달 불가. Causation 검증도 내부만.
- **개선**: BFF에 `/oov/approve`·`/validate/causation` 배선(계약 버전업). (=원래 ⑤.)

## 4. 순서 (단계별) — "저작 루프 라이브화" 스프린트

| 단계 | 태스크 | 내용 | 게이트 |
|:----:|--------|------|--------|
| 0 | **T-92** = P0 | 라벨→IRI 새니타이징 | 공백 라벨 저장 201 |
| 1 (핵심) | **T-93** = P1 + Causation 배선 · **T-94** = P2 | 저작 파생 오버레이 영속 + satisfy/컴파일러가 시드+저작 소비 + 온톨로지 타입 판정 | **satisfy 시드 회귀 그린 유지** + K2 저작 후 satisfy 판정이 실제로 바뀜 |
| 2 (안전·의미) | **T-95** = P3 · **T-96** = P4 | 저작 도메인 게이트·부정/증상부재·OOV 거부 + M1/M2 라우팅·RB 동적맵 | 저작 우회 차단 · 요구 M2/지식 M1 분리 · "없어야"가 반전 안 됨 |
| 3 (노출) | **T-97** = P5 | BFF `/oov/approve`·`/validate/causation` 배선 | UI에서 승인·인과 검증 도달 |
| 재측정 | ③′ | 13문장 재실행 | 저장 성공률·A/B 마진 회복 |

**의존**: T-92 → (T-93·T-94) → (T-95·T-96) → T-97 → ③′. 1단계가 최소 "새 지식이 산다" 증명, 2단계가 "올바르게", 3단계가 "UI에서".

## 5. 프레이밍 · 리스크

- **g3 롤백 아님** — g3.1은 시드 데모로 유효. 이 스프린트는 develop에서 "저작 루프 라이브화"로 진행.
- **satisfy 시드 회귀 = 상시 하드 게이트** — 새 배선이 시드 판정을 바꾸지 않는지 매 단계 확인(리팩터-그린).
- **재측정으로 닫는다** — ③′에서 저장 성공률과 A/B 마진 회복을 확인해야 스프린트 완료.

## 6. 열린 결정 (재현님)

- **한 번에 vs 단계적**: P0~P5를 한 스프린트로 vs **1단계(T-92·93·94)만 먼저 하고 ③′ 소형 재측정** 후 2·3단계.
- **내 권고**: **1단계 먼저.** 최소로 "새 지식이 저작→satisfy에 반영된다"를 증명하고 재측정한 뒤 2·3단계로 간다(큰 걸 작게 쪼개 리스크 관리). 1단계만 통과해도 제품 핵심 약속이 처음으로 실증된다.
