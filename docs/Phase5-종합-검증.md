## 2. OWL 활용 자기점검 (어디서 쓰이나)

| OWL 기능 | 사용 지점 |
|----------|-----------|
| punning(clabject) | 지식맵 층 구분(S-04), M1 개념=개체+클래스 |
| disjoint | 명세검증(S-02), 상위 온톨로지 일관성(S-07) |
| ∃ someValuesFrom | 필수속성 검증(S-02·S-03) |
| transitive | 지식맵 도출관계(has_part/has_subbehavior, S-04) |
| **subsumption(satisfy)** | **설계검증(S-03) — 핵심** |
| SHACL(CWA) 게이트 | 명세검증·satisfy 수치(S-02·S-03), 환각비교(S-05), 규칙(S-08) |
| SPARQL/규칙 | Q&A Layer A 규칙질문(S-05), 영향분석(S-07·S-08) |

→ OWL의 표현력이 **놀고 있는 지점 없이** 각 화면에 배치됨. satisfy가 핵심 활용점.

## 3. 모순·빈칸 점검

**충돌 없음 확인**
- 비목표(규정 PDF 추출·FMEA·파인튜닝)와 충돌하는 P0 기능 없음. 모든 시나리오가 6문장 시드 내 동작.
- 관리자 전용 기능(B*)은 권한 게이트로 P1/P2 경계 명확.

**해소됨 (Phase 1 v0.2에서 확정)**
- ✅ **저장모델**: RDF/SHACL 단일화(Neo4j 미채택).
- ✅ **satisfy 수치**: SHACL 게이트 + **구간 비교기**로 보완(3단계 결합). 비선형·연성 물리식(SMT)은 비목표(업그레이드 경로).

**이월/열린 항목 (→ 개발요구사항 단계)**
1. **RequiredBehavior 저작 UX**: 요구거동을 엔지니어가 어떻게 정의/선택하나 — 프리셋(겨울저소음·떨림없음, R1·R2) + 커스텀. S-03 상세 설계.
2. **규칙 ↔ SHACL 동기화**: DesignRule(6문장)과 SHACL shape의 단일 진실 소스·자동 생성 관계.
3. **지식맵 성능**: RDF/SPARQL 상에서 노드 증가 시 필터·레이아웃 전략.

## 4. 다음 단계 — 개발요구사항 정리 Agent 연결

이 6개 산출물(Phase 0~5)이 기존 **`02_개발요구사항_정리_Agent`** 의 입력이 된다.

```
[이번 재기획 산출]                    [개발요구사항 Agent 산출]
Phase 0 정렬 ─┐
Phase 1 백본 ─┤                       개발_요구사항_명세서.md (FR·NFR·가드레일)
Phase 2 시나리오 ─┼──▶ 개발요구사항 Agent ──▶ 기술_설계_명세서.md (아키텍처·State·API)
Phase 3 기능구조도 ─┤                  수용기준_및_테스트_시나리오.md (Given-When-Then)
Phase 4 화면설계 ─┤
Phase 5 종합 ─┘                       → 이후 03_dev_team 스쿼드로 병렬 구현
```

권장 순서: 위 열린 항목 1~5를 개발요구사항 Agent 초반 **갭 분석**에서 먼저 질의·확정 → SRS/기술설계 작성 → dev_team(계약 freeze → 병렬 구현 → 통합 게이트).
