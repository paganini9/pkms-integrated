# 설계 제안 — 온톨로지 밖 용어(OOV) 처리 & 논리 온톨로지 지속 진화

> 배경: T-73으로 `unknown_concept`가 **결정론적 온톨로지 소속 판정**이 됐다(온톨로지에 없는 개념 → fail-closed, insufficient). 안전하지만 무디다.
> 문제(재현님 제기): 도메인 온톨로지가 세상 모든 개념을 담을 수 없고, **엔지니어에게 "온톨로지 용어만 쓰라"는 제약은 부적절**하다. 엔지니어가 온톨로지에 없는 용어를 썼을 때, 제약하지 않으면서 (a) 매핑, (b) 확장, (c) 관리자 제안을 통해 **온톨로지를 지속 성장**시켜야 한다.
> 이 문서: 확립된 온톨로지 공학 방법론에 근거해 처리 모델을 제안하고, 기존 시스템(M0/M1/M2·제안형 자율성·거버넌스·리즈너·임베딩·T-85)에 어떻게 붙는지, 그리고 단계적 개발 반영안을 제시한다.

---

## 1. 핵심 원칙 — 맥락에 따라 정책을 분리한다

OOV(out-of-ontology) 용어의 "옳은 처리"는 **어느 맥락이냐**에 따라 정반대다. 지금까지 이 둘을 한 정책으로 묶어서 무뎌졌다.

| 맥락 | OOV 처리 | 이유 |
|------|----------|------|
| **① Q&A·설계검증 (접지/grounding)** | **fail-closed 유지** — insufficient, 환각 아님. provisional 개념은 접지 근거로 불인정. | T-73이 준 환각 안전성. 근거 없는 답을 지어내지 않는다. **바꾸지 않는다.** |
| **② 저작 (지식·요구 입력)** | **트리아지 → 매핑/확장/제안** — 엔지니어를 절대 막다른 길로 보내지 않는다. | 엔지니어는 자연어로 자유롭게 쓴다. OOV는 "오류"가 아니라 **"아직 온톨로지에 없음" = 성장 입력**. |

> 이 분리가 재현님이 지적한 긴장("엔지니어 비제약" ↔ "가드레일 유지")을 해소한다. 접지의 fail-closed는 그대로, **저작에서만** OOV를 생성적 진화 루프로 바꾼다.

## 2. 현재 상태와 한계 (근거)

- 온톨로지 어휘는 `rdfs:label` 하나뿐(한/영을 `"Rubber (고무)"`처럼 괄호로 묶음). **동의어·이형(異形) 층이 없다.** → 엔지니어가 "고무 블레이드", "고무 재질"처럼 조금만 달리 써도 어휘가 안 걸린다.
- T-73의 "정당한 도메인 어휘"(경도·압력·겨울철…)는 **코드 하드코딩 화이트리스트**. 새 어휘가 생길 때마다 코드를 고쳐야 하고, 온톨로지의 단일 진실원 밖에 산다.
- 결과: OOV = 무조건 fail-closed. 저작에서 엔지니어가 온톨로지에 없는 정당한 도메인 용어를 쓰면 **성장 기회가 버려진다**.

## 3. OOV 트리아지 — 5분류

저작 시 추출 개념이 온톨로지에 없으면, 막는 대신 **분류**한다:

1. **어휘 변이(synonym/variant)** — 기존 개념의 다른 표현("고무"↔"고무 블레이드"). → **어휘층에 altLabel 매핑**(로직 불변, 최빈·최경량).
2. **새 개념(기존 상위어 아래 들어감)** — 예: "발수 코팅"이 `Component`/`Material` 하위. → **subclass 삽입 제안**(리즈너로 위치 배치).
3. **새 관계** — 기존에 없는 인과·조건 관계. → **sub-property 삽입 제안**.
4. **범위 밖(일반/타도메인)** — "타이어", "자전거". → **정당한 거부**(가드레일의 본래 역할). 단 반복 등장하면 재검토 신호.
5. **모호** — 의도가 불분명. → **명료화 질문**(SRS 열린항목 #1 "명료화 질문 UX"와 직결).

## 4. 세 처리 경로와 방법론 근거

재현님이 짚은 세 시나리오(매핑 / 확장 / 별도 확장 온톨로지 제안)를 확립된 방법론에 매핑한다. "논리 온톨로지를 구축·확대하는 적절한 방법"을 그대로 채택한다.

### 4.1 경로 A — 매핑 (어휘층, SKOS)
- **방법**: **SKOS / SKOS-XL 어휘층**. 각 논리 개념(OWL Class)에 `skos:prefLabel` + 다수 `skos:altLabel`(ko/en, 이형·복합어). "surface 용어"와 "논리 개념"을 **분리**해, 엔지니어가 쓰는 표현 다양성을 로직을 건드리지 않고 흡수.
- 지금의 하드코딩 화이트리스트를 **온톨로지 데이터(altLabel)로 이관** → 단일 진실원 안으로, 코드 수정 없이 성장.
- **후보 생성**: 임베딩(로컬) 최근접 + 어휘 부분일치(안전 규칙 하) + LLM 매핑 가설 → HITL 확인. (프로젝트에 임베딩·LLM 이미 있음 = **온톨로지 정렬/매칭** 기법의 재사용.)
- 대부분의 OOV가 여기서 끝난다(가장 흔함·가장 쌈). 고신뢰 동의어는 경량 승인 또는 자동수용, 저신뢰만 큐로.

### 4.2 경로 B — 확장 (개념/관계 삽입 + 리즈너 배치)
- **방법**: **온톨로지 enrichment / 개념 삽입(concept insertion)**. 새 개념을 **가장 구체적인 기존 상위어의 subclass**로 넣고, **리즈너(HermiT)로 분류**해 위치를 계산한다. DL의 표준 개념삽입: 정의(최소 공리) → classify → (i) 일관성 확인, (ii) 위치 확정, (iii) **영향분석**(새로 생기는 subsumption·entailment) — 프로젝트 FR-12의 "M1 영향분석"이 바로 이것.
- **일관성 유지 메커니즘**: **Ontology Design Patterns(ODP) + OTTR(Reasonable Ontology Templates)**. 확장 유형별 템플릿(예: "증상 하위개념 추가", "인과관계 추가")이 **올바른 공리 + SHACL을 함께 방출**한다 → 프로젝트의 "문장→규칙→SHACL 단일소스 컴파일러" 철학과 동형. 이렇게 하면 확장이 **OWL 2 EL 프로파일 밖으로 새지 않는다**.
- 요구: 확장은 아무 공리나 손으로 쓰는 게 아니라 **템플릿 경유**. 관리자도 SHACL/공리를 직접 쓰지 않는다(기존 저작 원칙과 일치).

### 4.3 경로 C — 제안 큐 (거버넌스 있는 진화)
- **방법**: **DILIGENT** 방법론(분산·진화 온톨로지 공학). 로컬 제안(엔지니어) → 중앙 검토(관리자 보드) → 승인/거부 **+ 근거(argumentation) 로그** → 버전업. 이는 프로젝트의 **제안형 자율성 + 관리자 거버넌스 화면(FR-12/13/14) + 감사 로그** 와 정확히 포갠다.
- **스테이징(후보) 네임스페이스**: 미승인 개념/관계는 `cand:`(또는 M1-candidate) 네임스페이스에 **provisional**로 산다. 제안한 프로젝트의 **저작**엔 쓰이되 flagged, **타 프로젝트 satisfy·Q&A 접지엔 미포함**(격리). 리즈너를 core vs core+candidate로 돌려 **편입 전 영향 미리보기**.
- **반복 신호**: 동일 OOV가 여러 문장·프로젝트에 N회 등장 → 큐 우선순위 상향("이 용어가 자주 등장합니다 — 편입 검토").
- (참고 방법론: 전체 개발 프로세스는 **NeOn**(온톨로지 네트워크·재사용), 패턴은 **ODP**, 진화·거버넌스는 **DILIGENT**, 어휘는 **SKOS**. 우리 케이스엔 DILIGENT(거버넌스 루프)+SKOS(어휘)+ODP/OTTR(EL-안전 편집)+DL분류(배치) 조합이 최적.)

## 5. 아키텍처 — 기존 시스템에 붙는 지점

```
저작 입력(자연어)
  → 추출(Solar, json_object)                      [기존]
  → 개념 소속 판정(결정론)                          [T-73]
      ├─ in-domain → 그대로 저장 흐름                [기존]
      └─ OOV → ★트리아지★
            1) 임베딩+어휘 최근접 top-k 후보          [로컬 임베딩 재사용]
            2) LLM 매핑 가설 {synonym|subclass|relation|out|ambiguous}
            3) 저작 UI HITL 카드: "이 용어는 온톨로지에 없습니다 — 제안:"
                 · altLabel 매핑(경로 A)  · 새 개념/관계 추가(경로 B)  · 범위 밖  · 명료화 질문
            4) 승인 시:
                 · A → 어휘층 altLabel 추가(로직 불변)
                 · B → 템플릿(OTTR/ODP) 적용 → 리즈너 분류·일관성·영향분석 → SHACL 재생성 → T-85 영속
                 · 미승인/불확실 → cand: 스테이징(provisional, 접지 제외)
  → 관리자 거버넌스 큐(DILIGENT): 승인/대체매핑/사유거부/보류 + argumentation 로그  [FR-12/13/14]
```

- **Q&A/접지 경로는 무변경**: OOV·provisional은 여전히 insufficient(fail-closed). 승격된 개념만 접지 근거가 된다. **T-73 안전성 보존.**
- **T-85(상위 온톨로지 TTL 영속화)** 가 승인된 확장의 **영속 메커니즘** — 이 제안이 T-85에 온전한 목적을 준다.

## 6. OWL 2 EL + SHACL 안전성 유지

- 확장은 **템플릿 경유**라 EL-안전 공리만 생성(임의 표현력 유입 차단).
- 새 개념 삽입 = subsumption 배치 → EL 호환. 리즈너로 **일관성 + 무의도 subsumption(regression)** 검사(HermiT; EL 전용이면 ELK 대안, 현재 owlready2/HermiT+owlrl 폴백으로 충분).
- 규칙 있는 개념은 **단일소스 컴파일러**로 SHACL 재생성 — 손 SHACL 없음(기존 원칙).
- provisional은 격리 네임스페이스라 core 프로파일·성능을 오염시키지 않는다.

## 7. 단계적 롤아웃 (권장)

풀 진화 엔진은 연구급 규모다 — 와이퍼 6문장 MVP를 부풀리지 않도록 **얇게 먼저**.

**MVP 슬라이스(지금 반영 가능, 작음) — 신규 태스크 T-89 제안:**
1. **어휘층 도입** — 온톨로지에 `skos:altLabel` 추가, T-73 하드코딩 화이트리스트를 **온톨로지 데이터로 이관**. 소속 판정이 어휘층을 읽게.
2. **OOV 트리아지 카드(저작 UI)** — 매핑 제안(경로 A) + "관리자에 확장 제안"(경로 B/C 스텁, **provenance 기록**: 문장·프로젝트·빈도) + 명료화 질문 훅.
3. **접지 불변** — OOV·provisional은 insufficient 유지, 격리.
→ 효과: 엔지니어 **비제약** + 환각 **안전 유지** + 온톨로지 **성장 훅** 확보.

**풀 엔진(후속, Phase 4/포스트-MVP):**
- 리즈너 자동 배치·영향분석 UI, OTTR 템플릿 세트, DILIGENT argumentation 보드, 자동 정렬 후보, cand: 스테이징 격리 완비, 승인 시 자동 SHACL 재생성·버전.

## 8. 개발 반영 (제안)

- **신규 태스크 T-89(저작 OOV 트리아지 + 어휘층 + 제안 큐 MVP 슬라이스)** — 소유: 04(온톨로지/리즈너)·03(임베딩 후보)·07(저작 카드 UI)·05(제안 큐 API). Phase 3 릴리스 필수는 아님 → **릴리스 게이트 후 또는 Phase 3 말 옵션**으로 배치(핵심가치지만 MVP 경계 밖일 수 있어 재현님 판단).
- **열린항목 연결**: SRS #1(명료화 질문 UX)=트리아지 (e), #2(카테고리 고정 vs 사용자정의)=어휘·확장 거버넌스와 함께 결정.
- **기존과 통합**: FR-12(상위 온톨로지 편집·영향분석)·FR-13(규칙·SHACL 생성 뷰·카테고리)·FR-14(거버넌스)·T-85(TTL 영속)에 트리아지·제안 큐·어휘층을 얹는다(신규 서브시스템 아님, **기존 거버넌스의 입력원 추가**).

## 9. 리스크 · 완화

- **저작 마찰 증가**(매번 카드가 뜨면 피곤) → 고신뢰 synonym은 자동수용/경량 승인, **저신뢰만 큐**. 카드는 방해가 아니라 제안.
- **온톨로지 오염**(아무나 확장) → 스테이징 + 관리자 승인 + argumentation 로그. core는 항상 깨끗.
- **EL 밖 표현 유입** → 템플릿 강제(손 공리 금지).
- **provisional 누수**(미승인 개념이 답 근거로) → 접지에서 격리(안전 최우선). 이게 뚫리면 T-73 안전성이 무너지므로 **테스트로 못박기**(회귀셋에 "provisional은 insufficient" 케이스).
- **범위 팽창** → MVP는 슬라이스만. 풀 엔진은 명시적 후속.

## 10. 한 줄 요약

OOV는 오류가 아니라 **온톨로지 성장 신호**다. **접지에선 fail-closed 유지**(안전), **저작에선 매핑(SKOS 어휘층) → 확장(ODP/OTTR 템플릿 + 리즈너 배치) → 제안(DILIGENT 거버넌스 + T-85 영속)** 의 생성적 루프로 바꾼다. 엔지니어는 자유롭게 쓰고, 온톨로지는 통제된 방식으로 지속 성장한다.
