# 지식 저작 상호작용 + 프로젝트별 지식 범위 — 검토

> 작성일 2026-07-09 · 상태 draft-v0.1 · RB/단일소스 검토의 후속.
> 결정: **엔지니어의 편집 대상은 자연어 문장뿐**(규칙·SHACL은 파생·표시). **지식은 카테고리로 관리되고 프로젝트가 적용 지식을 선택**한다.

---

## 1. 저작 상호작용 — 문장 중심 파생

**진실원 사슬(재정의)**
```
자연어 지식 문장   ← 엔지니어의 유일한 편집 대상 (SoT)
   │ LLM (도움)
구조화 규칙 (DesignRule)   ← 파생·저장(rules.ttl). 사람이 직접 작성 X
   │ 컴파일러 (gen_shacl.py)
SHACL 게이트 + 인과엣지 + 사람뷰   ← 파생·실행. 사람이 직접 편집 X
```

- **엔지니어는 규칙/SHACL을 만지지 않는다.** 문장을 입력·수정하면 LLM→컴파일러가 규칙·SHACL을 다시 파생한다.
- **범위·조건 부담 완화**: 문장만으로 적용 범위·조건이 다 드러나지 않으므로, LLM이 해석(예: "겨울철·중형 SUV에 적용")을 **읽기 쉬운 형태로 제안**하고, 사람은 가정을 확인·보정하거나 **명료화 질문**에 답한다("모든 차종에 적용?"). SHACL/SPARQL은 노출하지 않는다.
- **엔지니어 뷰** = 문장 + "이 문장에서 이런 규칙·SHACL이 만들어졌다" 요약. 문장을 고치면 파생 결과가 실시간 갱신됨을 보여준다.
- `rules.ttl`은 손으로 쓰는 파일이 아니라 **LLM 파생 결과의 저장 형태**(감사·재컴파일용).

## 2. 지식 관리 — 카테고리 + 프로젝트 선택

- `KnowledgeSentence`는 **카테고리/그룹**으로 관리된다(예: 소음, 떨림; 확장 시 블레이드·암 등).
- **프로젝트는 적용할 지식(카테고리)을 선택**한다 — 모든 지식이 모든 프로젝트에 적용되진 않으므로.
- satisfy·검증은 **그 프로젝트가 선택한 지식의 규칙만** 사용한다.

## 3. 실증 — 프로젝트별 지식 범위 (`project_scope_demo.py`)

```
동일 설계 A(고무·600·8N·simple·SUV) — 프로젝트별 지식 범위 적용

프로젝트 A (겨울용 SUV · 소음+떨림 지식)  — 게이트 4개
   · 위반 4건: [S1] 소음, [S3,S5] 떨림, [S4] 떨림, [S6] 떨림
프로젝트 B (실내 진동시험 · 떨림 지식만)  — 게이트 3개
   · 위반 3건: [S3,S5] 떨림, [S4] 떨림, [S6] 떨림   ← 소음(S1) 미적용
```

→ **같은 설계·같은 데이터라도 프로젝트가 고른 지식 범위에 따라 검증 결과가 달라진다.** rules.ttl에 `dom:category`를 달고, 컴파일러가 프로젝트 선택 카테고리로 필터해 SHACL을 생성.

## 4. 화면·시나리오 반영 (Phase 2·4)

- **S-02 지식입력(도메인 지식, M1)**: 자연어 문장 입력 → 추출·검증 + **파생된 규칙·SHACL 요약(읽기 전용)** 표시. **편집은 문장 편집**, 저장 시 재파생. 규칙/SHACL 직접 편집 없음.
- **지식 브라우저(도메인 지식 영역)**: 카테고리별 문장 목록 → 문장 클릭 시 "이 문장에서 파생된 규칙·SHACL·인과엣지" 펼침. (지식맵 S-04와 연결.)
- **프로젝트 설정(M2)**: ① **적용 지식(카테고리) 선택** + ② 요구(RB, 자연어) + ③ 설계(DB). satisfy는 선택 지식 기준.
- **S-08(관리자)**: SHACL 빌더가 아니라 **규칙·SHACL 생성 뷰 + 카테고리 관리·파생 검토·영향분석**. raw-SHACL 직접 편집은 예외적 escape hatch(고급 전용).

## 5. 결론 & 남은 것
- 엔지니어 저작은 **문장 하나**로 단순화되고, 규칙·SHACL·지식맵·satisfy는 모두 그 파생. 프로젝트는 지식을 골라 적용.
- 남은 상세(구현 시): 명료화 질문 UX(모호할 때 LLM이 무엇을 되묻나), 카테고리 체계(고정 vs 사용자 정의), 문장 편집 시 하위 규칙 변경의 diff 표시.
